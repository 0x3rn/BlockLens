# BlockLens

BlockLens is a focused crypto market tool built with React, TypeScript, and Vite. It combines live CoinGecko spot-market data with precise price formatting, historical charts, asset comparison, device-local portfolio tracking, threshold alerts, and opt-in scenario-based AI research.

BlockLens is educational software, not a brokerage or financial adviser. Market data can be delayed, local alerts only run while the site is open, and AI briefs can be incomplete or wrong.

## What is implemented

- Global market capitalization, 24-hour spot volume, market-cap movement, Bitcoin dominance, active assets, and tracked exchanges from CoinGecko.
- Searchable, filterable, sortable top-100 market table with adaptive precision for micro-priced assets and pagination.
- Asset profiles with 7-day, 30-day, and 1-year price history; volume, SMA-20, and logarithmic chart controls; supply and market statistics.
- Trending assets and current 24-hour gainers/losers.
- Comparison of up to four assets using normalized “growth of 100” performance.
- A watchlist, portfolio quantities, cost basis, unrealized P&L, and CSV import/export. Signed-in users can sync these privately across devices; signed-out users remain device-local.
- Email/password accounts backed by Firebase Auth with private account data in Neon Postgres.
- Price and 24-hour movement alerts evaluated during the 60-second refresh while BlockLens is open.
- On-demand short-term, swing, and long-term AI analysis generated by a serverless function. Each horizon loads its own closed, verified spot-candle hierarchy, uses server-computed EMA, RSI, ATR, relative-volume, range, and trend inputs, then combines them with conditional Google Search-grounded catalysts. API credentials never ship to the browser, and generated briefs are saved in History for later review.
- Telegram AI analysis bot integration. `/ai_analysis` asks for Conservative or Risk before the short-term, swing, or long-term horizon picker; selecting a coin fetches fresh closed candles, runs the same Google Search-grounded Gemini analysis as the website, and includes verified source links when grounding is available.
- History for previous AI briefs and portfolio position activity. Signed-in users sync both history streams through the authenticated Neon API; signed-out users keep them in this browser.
- A paper-futures simulator with live Binance mark prices, virtual margin, leverage, liquidation protection, stop-loss/take-profit exits, and simulated execution history. It never submits exchange orders.
- URL-based navigation, route-level code splitting, a 404 page, resilient loading/error states, responsive navigation, keyboard focus styles, and reduced-motion support.
- Vercel Analytics and deployment security headers.

## Stack

| Layer | Technology |
| --- | --- |
| Client | React 19, TypeScript, React Router 7 |
| Tooling | Vite 8, Vitest, Testing Library |

## AI configuration

Website AI generation requires Turnstile verification before fetching analysis inputs or calling Gemini. Conservative and Risk use the same `ai_analysis` action and `/api/analyze` endpoint. Each submission sends `cf-turnstile-response`; both hosting adapters require Siteverify success, the expected action, and an exact allowed frontend hostname. The widget resets after every completed attempt. Telegram retains webhook authentication and shared quotas without a browser challenge.

Email/password sign-in and registration also require a fresh verification. Their submit buttons remain disabled until the widget succeeds; Google sign-in remains independent. Before invoking Firebase, the app sends only the token and operation to `/api/auth/verify`, which validates the exact `password_login` or `password_signup` action and allowed hostname on both hosting platforms. Tokens reset after each attempt or form switch. This uses the same three environment variables below. This protects the website's password forms; Firebase's public authentication API remains accessible directly, so provider-level abuse protection must be configured in Firebase separately.

Use the existing widget `0x4AAAAAAFSFBv33VMh4DpXy`. Configure these on **each deployment**:

| Variable | Placement | Production value |
| --- | --- | --- |
| `VITE_TURNSTILE_SITE_KEY` | Public build configuration | `0x4AAAAAAFSFBv33VMh4DpXy` |
| `TURNSTILE_SECRET` | Private runtime secret | The matching widget secret, stored through the platform secret manager |
| `TURNSTILE_HOSTNAMES` | Runtime configuration | `blocklens.corstack.dev` |

For Cloudflare, the `VITE_` value must be available during the Vite build, while the secret and hostname list belong to the Worker. For Vercel, configure all three environment variables for the appropriate environment and redeploy. A production hostname list must exclude `localhost`, `127.0.0.1`, and development hosts. Preview deployments need their own exact allowed frontend hostnames; no wildcard or request-header fallback is accepted.

For local testing, store the secret only in the ignored `.env.local`, set `TURNSTILE_HOSTNAMES=localhost,127.0.0.1`, and open an address allowed by the widget. Cloudflare's widget may allow the root `corstack.dev`, but the backend still needs the exact frontend `blocklens.corstack.dev`. Turnstile domains have no scheme, port, or path. Missing secret/hostnames fail closed; no automatic development bypass is installed. `public/_headers` and `vercel.json` allow Cloudflare's challenge script and iframe in CSP.

After configuring/deploying, submit with a fresh real token, then verify the same token is rejected on replay. Mocked unit tests do not substitute for this destination check. See the [existing-widget flow](https://developers.cloudflare.com/turnstile/spin/prompt.md) and [server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

Copy `.env.example` to `.env.local` for a local serverless environment, or configure the variables in the deployment platform:

```env
GOOGLE_CLOUD_PROJECT=your-google-cloud-project
GOOGLE_SERVICE_ACCOUNT_JSON={"type":"service_account",...}
FIREBASE_PROJECT_ID=your-firebase-project-id
DATABASE_URL=your-pooled-neon-postgres-url
```

For account sync, also add the Firebase web-app config:

```env
VITE_FIREBASE_API_KEY=your-firebase-web-api-key
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-firebase-project-id
VITE_FIREBASE_APP_ID=your-firebase-web-app-id
```

Apply all SQL files in `neon/migrations/` with `npm run db:migrate` on an isolated Neon branch first. The migration enables RLS for a restricted server role, caps persisted history, and provides the atomic AI quota used by both hosting adapters. Keep `DATABASE_URL` server-only; never use a `VITE_` prefix for database credentials.

The Google and Neon database variables intentionally have no `VITE_` prefix. Both credentials remain server-only. BlockLens obtains a short-lived Google Cloud access token and calls `google/gemini-3.7-flash` through Vertex AI. Each brief first attempts horizon-specific Google Search-grounded catalyst research; BlockLens incorporates it only when Vertex returns verifiable source metadata, otherwise it clearly remains technical-only. The prior DeepSeek client is retained only as commented code, matching the Vera integration.

The website offers three analysis horizons: Short-term (6 hours–3 days: 15m, 1H, 4H, 1D), Swing (3 days–4 weeks: 4H, 1D, 1W), and Long-term (1–12+ months: 1D, 1W, 1M). The server resolves verified spot symbols from CoinGecko ticker metadata. Node deployments prefer Binance and can fall back to Coinbase Exchange; the Cloudflare Worker uses Kraken's unauthenticated USD spot OHLCV endpoint because Binance and Coinbase restrict Cloudflare's network. It excludes open candles, validates OHLCV invariants, and fails explicitly when complete coverage is unavailable. Exchange-candle analysis currently requires USD display currency.

Conservative and Risk tabs select the analysis approach independently of the horizon. Conservative is the default and retains the existing prompts and model settings. Risk uses separate instructions to evaluate earlier momentum, breakout, and reversal setups without requiring full timeframe agreement; entries still need an evidence-backed trigger, invalidation, and explicit downside. Both approaches use the same verified inputs and confidence limits, and long-term analysis remains LONG or NO TRADE only. The optional `riskProfile` API field accepts `conservative` or `risk`; omitted values and older saved briefs default to Conservative. The selected approach is saved inside the existing history JSON, so no new environment variables or database migration are required. Telegram offers the same two approaches before the horizon picker and preserves the selection through paging and analysis; callbacks from older bot messages default to Conservative.

The Vite development server includes local adapters for `/api/account`, `/api/analyze`, the market snapshot, and the Telegram routes. Telegram still needs a public HTTPS tunnel or preview URL before Telegram can deliver webhook updates.



## Firebase authentication setup

Register a web app in your Firebase project and copy its config from **Project settings > Your apps** into the four `VITE_FIREBASE_*` fields in `.env.local`. Set `FIREBASE_PROJECT_ID` to the same value as `VITE_FIREBASE_PROJECT_ID` on every server deployment. In **Authentication > Sign-in method**, enable **Email/Password**, and add your production and development domains under **Authentication > Settings > Authorized domains**. Firebase web-app config is public; no Firebase service-account private key is needed for normal sign-in or server verification.

With `npm run dev` listening at `http://127.0.0.1:5173`, run `npm run auth:verify` to check live Firebase sign-up, sign-out, sign-in, authenticated Neon writes, account reload, and ownership enforcement. This creates a temporary test account and removes its Firebase user and Neon records afterward. Restart the dev server and rebuild after changing Firebase configuration.

Enable **Google** under Firebase Authentication's **Sign-in method** as well. Both sign-in and registration offer **Continue with Google**, using [Firebase's Google popup flow](https://firebase.google.com/docs/auth/web/google-signin). The same Firebase UID is used for Neon ownership, and new Google users get a profile on their first sync. Add each development and deployment hostname to **Authorized domains**, including `localhost` and `127.0.0.1` for the local dev URL. Popup cancellation, blocked popups, and conflicting sign-in methods show actionable messages; accounts are not linked automatically by application email matching. Test the Google chooser in a real browser: the automated live check exercises email/password auth, while unit tests cover Google flow wiring and errors.

Both hosting policies allow Firebase's popup helper script and the `blocklens-0x.firebaseapp.com` auth iframe, and use `Cross-Origin-Opener-Policy: same-origin-allow-popups` so the chooser can communicate with the app. If `VITE_FIREBASE_AUTH_DOMAIN` changes, update the exact `frame-src` host in `public/_headers` and `vercel.json` to match.

For this project's local Google sign-in preview, open `http://localhost:5173/account`: `localhost` is already authorized in Firebase. The server also listens on `127.0.0.1`, but that hostname must be added to Authorized domains before Google sign-in can be used from a `http://127.0.0.1:5173` browser URL.

Sign-up creates a signed-in email/password account. Sign-in is restored from Firebase's local persistence, and account API requests retrieve a fresh ID token from the SDK. The Node and Cloudflare adapters verify RS256 signatures against Google's cached signing certificates and validate issuer, audience, expiry, issued-at time, authentication time, and UID before entering the Neon RLS transaction. Issued-at and authentication timestamps allow five seconds of clock skew for freshly issued tokens; expiration remains strict. Verification follows [Firebase's ID-token requirements](https://firebase.google.com/docs/auth/admin/verify-id-tokens). Tokens are checked cryptographically; immediate revocation/account-disable checks are not enabled, so an already issued token may remain valid until it expires.

For existing Supabase accounts, import users into Firebase **before** asking them to sign in, preserving the original Supabase user ID as the Firebase UID. Firebase supports [imports of bcrypt password hashes](https://firebase.google.com/docs/auth/admin/import-users#import_users_with_bcrypt_hashed_passwords). This retains ownership of the Neon records whose IDs were converted from UUID to text by migration `0002_firebase_auth.sql`. Creating a new Firebase account with the same email does not retain the old UID; this app deliberately does not link records by email.

Set `SUPABASE_DATABASE_URL` and `GOOGLE_APPLICATION_CREDENTIALS` in `.env.local`; the latter is a path to a Firebase service-account JSON with user import/list permissions for the configured project. Keep that file outside Git or in the ignored `.migration-secrets/` directory. `npm run auth:import -- --check-access` checks Firebase admin read access independently of Supabase. Run `npm run auth:import` for a read-only preflight. It reads source users/identities in a read-only snapshot, preserves UUIDs, bcrypt hashes, verified emails, and Google subject IDs, and refuses colliding target emails, UIDs, or provider identities. Verified MFA factors, unsupported providers, phone/anonymous accounts, and passwordless email-only accounts stop the import for explicit handling. Active source bans become disabled Firebase accounts; their later re-enabling must be handled explicitly.

Pause writes and signups on **both** apps for final cutover. After a successful user preflight, run `npm run db:import -- --source-writes-paused`, then `npm run auth:import -- --apply --source-writes-paused`. User import verifies account identity fields and batch counts; its fingerprint permits retries after a partial Firebase import without overwriting existing accounts. It prints counts and checksums, never password hashes or user details. The database copy and Firebase user import are separate services and cannot commit atomically, so keep traffic paused until both reports are verified. Resume traffic after validating sign-in and account-record ownership.

The pause can be applied directly with `npm run migration:pause -- --firebase` followed by `npm run migration:pause -- --source`. The source guard blocks writes to all application/quota tables and changes to Supabase users/identities, while allowing reads. Firebase's original signup setting is saved in the ignored `.migration-secrets/firebase-signup-pause.json`. After import, run `npm run migration:verify` with the local API on port 5173; it compares all table counts/checksums and uses admin-minted Firebase tokens to verify each imported user's ownership through read-only API calls. These checks record verification sign-ins in Firebase without reading or resetting user passwords.

Restore Firebase's original signup setting with `npm run migration:pause -- --firebase --resume`. Keep the old Supabase database paused after cutover so stale clients cannot save changes there. If reverting to the old app is necessary, `npm run migration:pause -- --source --resume` restores source writes by making the guard function inactive; managed auth-table ownership and all existing source records are preserved. Reconcile any records written in Neon before reverting.

`npm run db:migrate` applies missing migrations once under a transaction and records their versions. Migration `0002` preserves account values, foreign keys, row-level policies, history bounds, and AI quotas. The checked-in Supabase migrations and the source database URL remain only for historical data import.

## Moving existing data to Neon

The [2026-10-07 import report](artifacts/migration-2026-10-07.json) records the completed import of three Firebase users, 26 application records, and three quota rows. All 11 table checksums/counts and each user's ownership through the local account API were verified. Firebase signups are enabled; Supabase records are retained with old writes paused. This import did not deploy the production application.

Fill the database and auth placeholders in the gitignored `.env.local`. Firebase handles sign-in and Neon stores all account records. Enable Email/Password in Firebase Console before using the account page. Database calls now go through `/api/account`; the server verifies each Firebase ID token, then executes the query under the restricted `blocklens_app` role with a transaction-local account ID. The browser never receives Neon credentials. New users get their Neon profile on their first authenticated sync. Firebase UIDs are stored as text; legacy UUID values are preserved.

1. Use an isolated branch of the existing Neon project for rehearsal. Put its pooled URL in `DATABASE_URL` and direct URL in `DATABASE_URL_UNPOOLED`.
2. Run `npm run db:check` (read-only), `npm run db:migrate`, and `npm run db:verify`. The migration runner refuses to adopt existing app tables and records successful schema versions. Verification exercises the HTTP transaction setup and account isolation, and rolls back all test writes.
3. Confirm the Supabase source has all historical migrations through `0004`. Set `SUPABASE_DATABASE_URL` to its TLS-enabled direct or session-pooler connection. For Supabase's private CA, download the certificate from Database Settings and add `sslmode=verify-full&sslrootcert=.migration-secrets/supabase-ca.crt` to the connection URI. Configure Firebase admin credentials and run `npm run auth:import` for a read-only collision check.
4. Pause writes and signups on both apps, including old browser sessions, during final import and cutover; importing a snapshot while writes continue can miss later changes. Run `npm run db:import -- --source-writes-paused` against the empty, migrated target, then `npm run auth:import -- --apply --source-writes-paused`. The database source transaction is read-only. The database importer preserves UUIDs, numeric precision, JSON ledgers, history, and quota counters, verifies every copied row by checksum and every table by row count, and rolls back target writes on mismatch. It refuses populated targets. Both importers log counts and hashes only. Keep traffic paused until both imports verify.
5. Deploy both the new server API and client with the destination `DATABASE_URL` and the Firebase values, then resume traffic. Test sign-in, sign-up, watchlist save/reload, portfolios, alerts, histories, and paper futures. Add the same pooled `DATABASE_URL` to every AI/Telegram hosting adapter so they share quotas. The source database remains available for rollback; do not delete it as part of this migration.

The direct Neon and source Supabase database URLs are local migration credentials only. Do not add them to client variables. Account deletion in Firebase does not automatically delete Neon records, so any future account-deletion flow must explicitly remove the Neon profile and its cascading records.

## Cloudflare Workers deployment

This repository can be deployed to either Vercel or Cloudflare Workers from the same commit. The Worker entrypoint is `worker/index.ts`; it serves the Vite build in `dist/` through the `ASSETS` binding and handles the dynamic API routes. Vercel continues using the handlers in `api/`. The market, AI, and Telegram logic is shared under `api/`.

In Cloudflare Workers Builds, use the repository root (`/`), set the build command to `npm run build`, the deploy command to `npx wrangler deploy`, and the non-production version command to `npx wrangler versions upload`. The checked-in `wrangler.jsonc` configures `dist/` as Worker static assets, sends `/api/*` requests to the Worker first, and falls back to `index.html` for client-side routes.

Add the server values as encrypted environment variables for both preview and production:

```env
GOOGLE_CLOUD_PROJECT=your-google-cloud-project
GOOGLE_SERVICE_ACCOUNT_JSON={"type":"service_account",...}
FIREBASE_PROJECT_ID=your-firebase-project-id
DATABASE_URL=your-pooled-neon-postgres-url
# Optional; leave both unset for the keyless public API
# COINGECKO_API_KEY=your-coingecko-key
# COINGECKO_API_PLAN=demo
TELEGRAM_BOT_TOKEN=your-bot-token
TELEGRAM_WEBHOOK_SECRET=a-long-random-secret
```

The Worker uses the Web Crypto API for Vertex AI service-account authentication, so it does not depend on the Node Google Auth client at runtime. The Worker route handler is kept separate from Vercel’s adapter, while the validation, market-data, Telegram, and AI modules remain shared.

`COINGECKO_API_PLAN` is `demo` for a free Demo key (the default when a key is present) or `pro` for a paid Pro key. Demo keys use `https://api.coingecko.com/api/v3` with the `x-cg-demo-api-key` header; Pro keys use `https://pro-api.coingecko.com/api/v3` with `x-cg-pro-api-key`. Leave both variables unset to use CoinGecko's keyless public API, which is rate-limited and intended for light use. Do not set the key to the literal word `optional`.

Server-side requests retry once through the keyless public endpoint when CoinGecko rejects the configured key with `401` or `403`; rate-limit and upstream-server errors are not duplicated.

When moving `blocklens.somto.xyz` between providers, keep the same paths (`/api/analyze`, `/api/telegram/webhook`, and `/api/telegram/coins`). Update the domain’s DNS/custom-domain attachment to the active deployment. The Telegram webhook URL can remain `https://blocklens.somto.xyz/api/telegram/webhook` as long as that route exists on whichever provider is active.

## Telegram bot setup

The bot uses a webhook, so it works with Vercel serverless functions without a long-running polling process. Create a bot with BotFather, then add these server-only variables to the deployment:

```env
TELEGRAM_BOT_TOKEN=your-bot-token
TELEGRAM_WEBHOOK_SECRET=a-long-random-secret
```

Register the webhook once through the Telegram Bot API, replacing the placeholders with your values:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook?url=https://<your-domain>/api/telegram/webhook&secret_token=<TELEGRAM_WEBHOOK_SECRET>
```

Register the bot's command menu after setting `TELEGRAM_BOT_TOKEN` in `.env.local`:

```bash
npm run telegram:commands
```

Users can send `/ai_analysis` to choose Conservative or Risk, then a horizon and coin. The direct commands `/short_term_trade` (6 hours–3 days), `/swing_trade` (3 days–4 weeks), and `/long_term_trade` (1–12+ months) ask for an approach first, then open coins with that duration already selected. The previous `/ai_short`, `/ai_swing`, and `/ai_long` commands plus the legacy `/ai-analysis` alias remain supported when typed manually. The bot reads the same top-100 CoinGecko snapshot as the website, shows 12 coins per page, preserves the selected approach and horizon while paging, and runs the same server-side Gemini instructions as the website after a coin is selected. Briefs identify the selected approach, and users can change it or the horizon from the coin list and results. Grounded results include current coin and macro catalysts plus verified source links; if Google Search grounding is unavailable, the bot labels the result technical-only instead of presenting unverified news. The public coin-list endpoint is available at `/api/telegram/coins` for operational checks. Telegram user IDs are not automatically BlockLens account IDs; account-linked history should only be added after an explicit linking flow.

## Data and privacy behavior

- CoinGecko supplies public market snapshots and history; the initial snapshot is cached server-side and no CoinGecko key is stored in the client.
- Signed-out watchlists, positions, paper-futures trades, history, alert rules, and display currency stay in this browser and synchronize only across tabs on the same origin. Signed-in watchlists, positions, paper-futures trades, history, and alert rules hydrate from Neon through `/api/account` and persist only to the user's account; watchlist changes are shown as saved only after the Neon API confirms them. Display currency is session-only for signed-in users.
- Firebase's own auth session may remain in its client-managed storage so a user can stay signed in after reopening the browser; this stores authentication state, not portfolio or trading records.
- Portfolio CSV export is generated entirely in the browser.
- Alerts are not push notifications and do not run in the background after the page closes.
- Only the selected asset snapshot, validated closed exchange candles, deterministic indicator summaries, sampled CoinGecko context, and verified catalyst records are sent to the AI provider when the user explicitly requests a brief.
- The AI endpoint validates payload size and shape, applies a bounded local concurrency guard plus an atomic per-caller/global Neon quota, and disables response caching.

## Routing and deployment

Client routes are defined in `src/App.tsx`. `vercel.json` preserves deep links with an SPA fallback; Vercel’s filesystem precedence keeps `/api/analyze.ts` available as a function. Configure the project as Vite with `dist` as the output directory.

Before deployment:

1. Run `npm test` and `npm run build`.
2. Add `GOOGLE_CLOUD_PROJECT`, `GOOGLE_SERVICE_ACCOUNT_JSON`, and `DATABASE_URL` as server-side environment variables if AI trading analysis should be enabled.
3. Add `FIREBASE_PROJECT_ID` on the server and the four `VITE_FIREBASE_*` web-app values for client sign-in. Both project-ID values must refer to the same project. Apply the Neon schema and import existing data before deploying the new account API.
4. Verify `/`, `/markets`, `/analysis`, `/watchlist`, `/history`, `/futures`, `/compare`, `/account`, an asset route, and `/api/analyze` on a preview deployment.

## Known operational limits

- CoinGecko’s public API can rate-limit frequent requests; BlockLens caches and deduplicates calls and keeps the last successful snapshot visible when refreshes fail.
- AI generation fails closed if the shared Neon quota is unavailable. The checked-in quota allows eight requests per caller per minute and 2,000 total requests per UTC day; tune those constants in Neon migration `0001_blocklens.sql` before applying it if the deployment needs different budgets.
- Account sync is opt-in and requires Firebase web-app values, the server project ID, the server-only Neon connection, and the Neon schema. Without auth configuration, the local fallback remains active. Signed-in sync fails visibly when Neon is unavailable.
